# Длительная проверка пяти физических клиентов

**Статус: стенд подготовлен, реальный прогон ещё не выполнен.** Проверки пяти
сессий на одном телефоне и Xiaomi → эмулятор не заменяют этот эксперимент.
Измерения нужны до выбора поддерживаемого качества и адаптации bitrate/FPS.

Нужны шесть физических Android 13+ устройств: сервер и пять клиентов, одна Wi-Fi
сеть без изоляции клиентов, USB ADB и Python 3.10+. Эмуляторы runner отклоняет.
На всех устройствах должны быть установлены одни и те же свежие universal debug
APK приложения и тестов. Runner сравнивает SHA-256 установленных APK между всеми
устройствами и с локальными build outputs. Интернет-сервер не используется.
VPN настраивает пользователь; runner его не изменяет.

## Подготовка

Из корня репозитория собрать текущую ветку:

```powershell
.\gradlew.bat :app:assembleDebug :app:assembleDebugAndroidTest --max-workers=1
```

Установить оба APK на каждый из шести serial, например официальным Android CLI:

```powershell
$android = 'C:\Users\akma3\AppData\AndroidCLI\android.exe'
$serial = 'SERIAL'
& $android install --device=$serial --apks=app/build/outputs/apk/debug/app-debug.apk --install-options=-g
& $android install --device=$serial --apks=app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
```

`-g` выдаёт runtime-разрешения для тестового запуска. Камера нужна серверу;
на Android 17 нужен также доступ к локальной сети. Разблокировать телефоны,
проверить разрешения, остановить существующую трансляцию и освободить место для
CSV. Тест удерживает экран включённым, клиент использует настоящий ViewModel и
Compose/SurfaceViewRenderer. Начальный уровень заряда, яркость, комнатную
температуру, питание USB и модель роутера записать отдельно в итоговый отчёт.

## Запуск

Вначале можно проверить аргументы без вызовов ADB:

```powershell
python tools/run_five_device_soak.py --host HOST --clients C1 C2 C3 C4 C5 --server-host 192.168.0.193 --dry-run
```

30 минут, Camera2, без изменений Wi-Fi:

```powershell
python tools/run_five_device_soak.py --adb 'C:\Users\akma3\AppData\Local\Android\Sdk\platform-tools\adb.exe' --host HOST --clients C1 C2 C3 C4 C5 --server-host 192.168.0.193 --duration 1800 --backend camera2
```

Отдельно повторить с `--backend ndk`. Для проверки восстановления одного клиента
добавить `--outage-client 1 --outage-after 300 --outage-seconds 4 --allow-wifi-toggle`.
Это явно разрешает временно выключить Wi-Fi только на выбранном клиенте.
Включение выполняется после паузы и повторяется в finally при сбое. Отключение
устройства от USB может помешать восстановлению; ошибки cleanup попадают в отчёт.
Остальные клиенты должны продолжать получать видео во время обрыва.

Runner не устанавливает приложения, не запускает эмуляторы и не меняет VPN.
После read-only preflight он запускает instrumentation на всех шести телефонах.
Для WSS отпечаток и код передаются через доверенное USB-подключение: временный
файл в приватном каталоге сервера читается через `run-as` и удаляется. NSD не
используется для доверия. Координационные секреты не попадают в CSV/summary.
При завершении/сбое runner останавливает `dev.localstream` на запущенных им
устройствах и собирает частичные результаты. Сбой одного cleanup не должен
мешать остальным попыткам очистки. USB credentials не предназначены для release.

## Метрики и критерии

Замер сервера начинается после пяти CONNECTED PeerConnection, каждый из которых
уже закодировал кадры. По умолчанию 1800 секунд, с выборкой каждые 2 секунды:

- Для каждого PeerConnection: поколение, состояние, RTP bytesSent, framesEncoded,
  totalEncodeTime, encoder FPS и qualityLimitationReason.
- Общие счётчики UID TX/RX, температурный статус Android, температура батареи,
  signed current, charge counter, energy counter и подключённое питание.
- На каждом клиенте: фаза, полученные кадры/FPS, попытки подключения и длительность
  отсутствия прогресса. FPS считается по дельте кадров и реальному монотонному
  интервалу выборки, а не по номинальному таймеру UI. Это **received FPS**,
  не измерение renderer FPS.
- При выбранном обрыве — первое наблюдение новых кадров после команды включения
  Wi-Fi, с точностью выборки 2 секунды; это не точный timestamp первого пакета.

Базовые критерии: все шесть instrumentation-тестов прошли; каждый клиент получил
явное ENDED после длительного замера; не менее 90% клиентских выборок имеют
минимум 15 полученных FPS (`--minimum-fps`); ни один обрыв кадров не дольше 20 с;
пять CONNECTED наблюдались минимум в 95% серверных выборок; есть пять измеренных
дельт RTP bytesSent для агрегированного bitrate; нет статуса SEVERE или выше
(`thermalStatus >= 3`) ни на одном устройстве. Это критерии стенда для оценки,
а не уже подтверждённая гарантия продукта.

RTP bitrate считается по разностям bytesSent и монотонного времени. После смены
generation база сбрасывается. Его нельзя считать полной нагрузкой на радио:
для этого отдельно сохраняются UID TX/RX. Пустые поля означают отсутствие
измерения. Температура батареи не является температурой CPU; USB/зарядка влияют
на ток и энергию. Расход Wh выводится только при непрерывном отсутствии питания
и доступном убывающем energy counter. Не делать вывод об автономности по USB-прогону.

Результаты: `artifacts/validation/load/<runId>/summary.json`, CSV по ролям и
instrumentation logs. Каталог исключён из Git. В отчёте есть модели/API и хэши
APK, но нет access code, токенов, приватного ключа или видео. Для публикации
подготовить отдельный Markdown-отчёт с условиями и результатами, проверить его
и приложить к PR. Если тест не пройден, сохраняются и частичные данные.
Если копирование CSV на ПК не удалось (например, закончился диск), приложения
всё равно останавливаются, а исходный CSV остаётся в приватном каталоге телефона;
путь записывается в `uncollectedDeviceCsv`. Успешно скопированные CSV удаляются
с устройств. Координационные секреты удаляются независимо от результата копирования.

## Проверки самого стенда без устройств

```powershell
python -m unittest discover -s tools -p 'test_*.py' -v
.\gradlew.bat :media:testDebugUnitTest :app:assembleDebugAndroidTest :app:lintDebug
```

Обычный запуск всей instrumentation suite пропускает длительные тесты, пока не
передан `soakOptIn=true`. Физический прогон нужно выполнить отдельно на обеих
реализациях камеры. До этого нагрузочная задача остаётся незавершённой.
